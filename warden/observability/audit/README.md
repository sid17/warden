# Audit — Offline Safety Analysis

On-demand hook-based logging that captures what the agent did during a pipeline run. Activated via `AUDIT_ENABLED=1`. Answers: which tools were called, on which files, by which agent — and should we restrict that?

## How It Works

```
Pipeline run (unrestricted, AUDIT_ENABLED=1)
  → Claude SDK hooks / OpenHarness command hooks fire on every tool call
  → JSONL events appended to logs/{run-id}.jsonl
  → aggregate.py reads JSONL across 2-3 runs → audit report
  → Human/agent reads report → derives per-agent safety configs
```

The audit system uses each provider's native hook mechanism:
- **Claude**: async Python callbacks registered on `ClaudeAgentOptions.hooks` — in-process, zero subprocess overhead
- **OpenHarness**: command hooks via `HookExecutor` — spawns `python -m warden.observability.audit.openharness_hook_handler` which receives payload via `$OPENHARNESS_HOOK_PAYLOAD`

Both produce identical JSONL output using the shared `AuditEvent` schema (`schemas/audit.py`).

## Structure

```
audit/
├── claude_sdk_hooks.py           # Async callbacks for 7 Claude SDK event types
├── openharness_hooks.py          # HookExecutor with command hooks for 5 event types
├── openharness_hook_handler.py   # Subprocess entry point for OpenHarness hooks
├── aggregate.py                  # Cross-run aggregation → audit report
├── scan_output.py                # Output scanner for leaked internals
├── logs/                         # Raw JSONL — one file per run
│   ├── course-run-1.jsonl
│   └── smoke-*.jsonl
└── reports/                      # Generated outputs — one folder per audit
    └── course-creation-v14/      # Example: first audit (course creation workflow)
        ├── run-manifest.md       # What was run, prompts used, constraints
        ├── audit-report.md       # aggregate.py output — tool matrix, path map, convergence
        ├── safety-config-guide.md# Per-agent SDK config recommendations
        └── findings.md           # Status: what's ready, what needs testing
```

## Per-Audit Report Structure

Each time you audit a new workspace or workflow, create a folder under `reports/`:

```
reports/{workspace-name}/
├── run-manifest.md           # Step 1: record what you ran and why
├── audit-report.md           # Step 3: generated by aggregate.py
├── safety-config-guide.md    # Step 5: derived SDK configs from report
└── findings.md               # Step 6: deployment status and next steps
```

Name the folder by workspace or workflow (e.g., `course-creation-v14`, `study-assistant`, `code-review-pipeline`). This keeps audits isolated — you can compare across workspaces and re-audit without overwriting previous results.

## What Gets Captured

Each JSONL event records (OTel-aligned field names):

| Field | Example |
|-------|---------|
| `event_type` | `PreToolUse`, `PostToolUse`, `SubagentStop` |
| `agent_id` | `course-builder-agent` |
| `agent_type` | `main`, `sub-agent` |
| `tool_name` | `Write`, `Bash`, `Read` |
| `tool_input_summary` | `{"file_path": "courses/ch1.md"}` (large content stripped) |
| `tool_output_summary` | `File written (2.3kb)` (truncated) |
| `gen_ai.tool.name` | `Write` (OTel dot notation) |
| `gen_ai.agent.name` | `course-builder-agent` |

## Aggregation Report Sections

`aggregate.py` reads JSONL from multiple runs and produces four analysis sections:

| Section | What it produces |
|---------|-----------------|
| **Tool Usage Matrix** | Per-agent tool call counts — unused tools are candidates for `disallowed_tools` |
| **Path Access Map** | Per-agent read/write file paths — paths outside expectations are anomalies to restrict |
| **Command Inventory** | Per-agent Bash commands with sensitive command flagging |
| **Convergence Analysis** | Tool stability across runs — <80% means agent behavior varies, widen permissions |
